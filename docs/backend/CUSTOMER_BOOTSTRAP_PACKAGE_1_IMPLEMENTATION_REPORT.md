## 3. The baseline migration

Generated via `alembic revision --autogenerate` against an empty, isolated schema (see §4 for why a schema rather than a second database) with all 8 existing models imported. It contains a straightforward `op.create_table(...)` for each of `organisations`, `knowledge`, `users`, `workers`, `chat_sessions`, `knowledge_permissions`, `worker_memories`, `chat_messages`, and the exact reverse `op.drop_table(...)` sequence for `downgrade()`. Every column, type, nullability, primary key, foreign key, and unique constraint was checked by hand against the actual model source (`models/*.py`) and matches exactly — this migration adds nothing beyond what `create_tables.py` already produces today.

## 4. Implementation notes and one real bug found and fixed

- **`env.py` sources `DATABASE_URL` from the application's own `config.py`**, not a second URL hardcoded in `alembic.ini` — one source of truth for which database is targeted, matching the plan's own stated intent ([[customer-bootstrap-implementation-plan-v1]] §7).
- **A real bug, found and fixed during implementation, not merely anticipated:** the first attempt routed the URL through `alembic.Config.set_main_option()`, which writes into a `ConfigParser`-backed section. `ConfigParser` treats a literal `%` in a value as the start of an interpolation sequence — this raised `ValueError: invalid interpolation syntax` the moment a URL containing a `%`-encoded query string (or, in principle, any database password containing a `%` character) was used. Fixed by building the engine directly from the plain `DATABASE_URL` string (`create_engine(DATABASE_URL, ...)` / `context.configure(url=DATABASE_URL, ...)`), bypassing `ConfigParser` interpolation entirely. This is now documented in `MIGRATIONS.md` so a future contributor doesn't reintroduce it by "simplifying" back to `set_main_option`.
- **A privilege limitation discovered in this environment:** the application's Postgres role (`teracom_admin`) does not have `CREATEDB` (confirmed — `createdb teracom_ai_test` failed with "permission denied to create database"). This meant the project's own documented convention of a separate `teracom_ai_test` database (referenced in `.env`/`config.py`'s `TEST_DATABASE_URL`) could not be created in this session. **Resolution:** both the baseline-migration verification and the automated test (§6) use a **disposable Postgres schema** inside the existing `teracom_ai` database instead of a separate database — this requires only the ordinary `CREATE` privilege the role already needs to own its own tables, works identically in any environment (including one without superuser access), and is arguably a better long-term design for migration testing specifically than depending on a privilege the app's normal role shouldn't need. This is documented in `MIGRATIONS.md` and does not use or depend on `TEST_DATABASE_URL` at all.

## 6. Validation

### Build
`./venv/bin/python -c "import main"` succeeds and returns a valid `FastAPI` app object — confirmed after all changes above, so adding Alembic did not break the application's own import path. (The Hugging Face rate-limit warning and embedding-model loading output on that command are pre-existing `sentence-transformers` behaviour, unrelated to this change.)

### Tests
`./venv/bin/pip install pytest` (not previously installed — this backend had no test framework at all before this task) then `./venv/bin/python -m pytest tests/test_migrations.py -v`:

```
tests/test_migrations.py::test_upgrade_head_creates_exactly_the_current_models PASSED
tests/test_migrations.py::test_downgrade_base_removes_every_model_table PASSED
2 passed in 2.59s
```

Both tests create their own disposable schema and drop it afterward (`CASCADE`), regardless of pass/fail, so no residual state is left behind by running them.

### Migration verification
Performed manually, end to end, against an isolated `alembic_test` schema before the automated tests existed, then again via the automated tests above:

1. `alembic upgrade head` against the empty schema → created exactly the 9 expected tables (8 model tables + `alembic_version`) — confirmed by querying `information_schema.tables`.
2. `alembic downgrade base` → removed all 8 model tables, leaving only the (now-empty) `alembic_version` table — confirmed the same way.
3. `alembic upgrade head` re-run to confirm the migration is idempotent/re-runnable from a clean state.
4. **The real dev database (`teracom_ai`, `public` schema, which already had all 8 tables and whatever data prior sessions' smoke testing left in them) was stamped, not upgraded:** `alembic stamp head` — this only wrote to a new `alembic_version` bookkeeping table; `information_schema.tables` was checked before and after and confirms no existing table, column, or row was touched. `alembic current` now correctly reports `c189cc03c84e (head)` for this database.
5. The temporary `alembic_test` schema used for manual verification was dropped after use; it was not left behind.

- **No CI wiring** — `pytest` runs locally only; there is no CI configuration in this repository to run it automatically. Out of scope for this package.
