## 2. Customer signup flow / organisation creation flow / first administrator creation

These three requested items are one mechanism, not three: `POST /signup` (`api/signup.py`, new) takes `{organisation_name, admin_first_name, admin_last_name, admin_email, admin_password}` and, in one flow:

1. Rate-limits by client IP (see §6).
2. Rejects an already-registered email with `409`, *before* attempting to create anything (the common case, checked directly).
3. Derives a URL-safe slug from `organisation_name` (lowercase, non-alphanumeric runs collapsed to `-`), creates the `organisations` row with `status = "pending_licence"`, and retries with a numeric suffix (`-2`, `-3`, …) up to 5 times on a slug collision — this is also the fallback path for the same-email race (see §6) that the pre-check doesn't catch.
4. Creates exactly one `users` row for the request's admin fields, `role = "admin"`, `organisation_id` set to the just-created organisation, password hashed via the existing `hash_password` (`auth/security.py` — reused, not reinvented).
5. Commits both rows in the same transaction (a slug collision or email race rolls back cleanly via `db.flush()`/`db.rollback()` before anything is committed).
6. Returns `{access_token, token_type}` using the existing `create_access_token()` — identical shape to `POST /auth/login`'s response, so the eventual frontend (Package 4, not built here) can reuse the same session-cookie-setting code path with no new mechanism.

There is no separate "become administrator" step — per [[customer-bootstrap-architecture-v1]] §4, the first user of a brand-new organisation simply *is* created with `role = "admin"`; there is no one else to be gated by.

## 4. Required backend API endpoint — implemented

`POST /signup` (`api/signup.py`, registered in `main.py` alongside the other 40 routers, same `include_router` pattern). No new registration mechanism was introduced. This is the **only** endpoint in this backend with no `Depends(require_role(...))` guard — a deliberate, narrowly-scoped exception, exactly as [[customer-bootstrap-architecture-v1]] §16 specifies, and reviewed as such in §6 below.

## 5. Required validation — implemented, plus two pre-existing bugs fixed

- **Request validation:** `schemas/signup.py`'s `SignupRequest` rejects blank names/organisation name/email (`field_validator`, trims whitespace) and passwords under 8 characters — both return FastAPI's standard `422`, not a crash.
- **Two pre-existing unhandled-`IntegrityError` bugs, identified in [[customer-bootstrap-architecture-v1]] §3 and explicitly named in the plan's Package 2 scope, fixed alongside the new endpoint:** `POST /organisations/` (a duplicate `slug`) and `POST /users/` (a duplicate `email`) both previously surfaced as a raw, unhandled `500`. Both now catch `IntegrityError`, roll back, and return a `409` with a clear message — same fix shape as the new signup endpoint's own collision handling, applied to the two existing admin-gated endpoints that had the identical root cause.
- **A deliberate trade-off decision, made explicitly rather than left implicit:** [[customer-bootstrap-architecture-v1]] §8 flagged, but did not resolve, whether a duplicate-email signup attempt should return a specific "already registered" message (usable, but confirms the email's existence to an anonymous caller) or a generic response (private, but confusing for a genuine user who mistyped). This implementation returns the specific message — consistent with how the vast majority of B2B signup flows behave, and because this backend has no consumer-privacy requirement stated anywhere that would outweigh the usability cost. This is a judgment call made during implementation, not something [[customer-bootstrap-implementation-plan-v1]] resolved in advance — flagged here for [[cybersecurity-worker]] to revisit if that judgment is wrong for this product.

## 6. Security review of the deliberate `require_role` exception

- `POST /signup` never touches an existing organisation's data — every row it writes is newly created within the same request. It cannot be used to inject a user into an *existing* organisation (it always creates a fresh one), so it does not weaken the multi-tenant isolation model described in [[licensing-service-architecture-v1]] §22.6.
- **Rate limiting, not duplicated but shared:** `auth/rate_limit.py`'s `LoginRateLimiter` was refactored to extract its sliding-window core into a new `SlidingWindowRateLimiter` base class (byte-for-byte identical behaviour — same `_key`, same public method signatures for `LoginRateLimiter`, so nothing calling `login_rate_limiter` elsewhere changes). A new `SignupRateLimiter` (keyed by IP alone, since there's no existing account to key against yet) reuses the same core, configured via new `SIGNUP_MAX_ATTEMPTS`/`SIGNUP_ATTEMPT_WINDOW_SECONDS`/`SIGNUP_LOCKOUT_SECONDS` env vars (documented in `.env.example`, same `os.getenv(...)`-with-default convention as the existing `LOGIN_*` vars) — defaulting to 5 attempts per hour, then a 1-hour lockout.
- **What this package does *not* address**, restated from [[customer-bootstrap-architecture-v1]] §17, not silently resolved: no CAPTCHA/bot protection, no email verification. Both remain explicit Open Decisions; rate limiting is the only abuse control shipped in this package.

## 7. Validation

### Build
`./venv/bin/python -c "import main"` succeeds after every change in this package, returning a valid `FastAPI` app object.

### Tests
`./venv/bin/python -m pytest tests/ -v` — **8 passed** (the 2 pre-existing Package 1 migration tests, unchanged, plus 6 new signup tests): happy path (organisation created with `status="pending_licence"`, returned token works against `GET /auth/me`), duplicate email → `409` not `500`, duplicate organisation name → two distinct auto-suffixed slugs, missing fields → `422`, short password → `422`, and rate-limit lockout → `429` with a `Retry-After` header (verified by seeding a real duplicate-email account first, then forcing `_max_attempts` down to 2 for a deterministic, fast test, restored afterward). All tests run against a disposable, per-test Postgres schema migrated via the real Alembic migrations (`tests/conftest.py`, extending Package 1's isolated-schema pattern to full API tests via a `get_db` override) — none touch the real database.

### API verification
Performed against a live `uvicorn` process (not just the test client), with cleanup afterward:

1. `POST /signup` with a fresh email → `201`, `access_token` returned.
2. That token against `GET /auth/me` → `200`, `role: "admin"`, correct `organisation_id`.
3. Repeating step 1 with the same email → `409`, "already exists".
4. Repeating step 1 with the same `organisation_name` but a new email → `201`, and the two resulting organisations were confirmed (direct SQL) to have distinct slugs (`verification-co`, `verification-co-2`).
5. A payload missing every field except `organisation_name` → `422` with field-level error detail.
6. Direct SQL confirmed both created users' `password_hash` values are bcrypt hashes (`$2b$12$...`), never the plaintext password.
7. **Cleanup:** both verification users and both verification organisations were deleted afterward; a final count query confirmed zero rows remain from this verification. The server process was then stopped.
8. The pre-existing dev organisation (`Teracom AI`, created before this session) was confirmed unaffected throughout — its `status` is `"active"` (from the migration's backfill default, §3), not touched by any of the verification calls above.
