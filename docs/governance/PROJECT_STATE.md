## 1. What Teracom AI is

Teracom AI is the product build-out of `teracom-ai-frontend` (public marketing/commerce site, package name `teracom-commerce-platform-v3`) into an authenticated multi-tenant platform backed by a separate repository, `teracom-ai-backend` (FastAPI + PostgreSQL + Chroma + Ollama). The platform's core object is a **Worker** — an AI agent persona (name/role/purpose/instructions) scoped to an organisation, with its own knowledge assignments, chat sessions, and memory. See [[worker-catalogue]] for the currently approved roster of worker types and [[frontend-architecture]] for the full technical design.

Two repositories exist:

- **`teracom-ai-frontend`** (this repo) — Next.js 14 App Router, plain JavaScript, one global stylesheet, Stripe checkout, Zoho invoicing, and (newly) an authenticated `/portal` product surface.
- **`teracom-ai-backend`** (separate repo, not present here) — FastAPI, SQLAlchemy/PostgreSQL, JWT auth, Chroma vector store, Ollama for chat. Reviewed in detail by `FRONTEND_ARCHITECTURE_V1.md` Part B; no source files from that repo are checked into this one, so backend documentation in this knowledge base is necessarily second-hand (see [[backend-status]]).

## 3. Backend state — mostly as documented; Knowledge's, Chat's, Memory's, Administration's, and Connectors' endpoints independently verified; Billing & Licensing confirmed to not exist at all

The backend repository is not part of this git repository, but a checkout of it is available on disk in this environment (sibling directory `teracom-ai-backend`) and was read directly while building Package 4 (Knowledge), Package 5 (Chat), Package 6 (Memory), Package 7 (Administration), Package 8 (Connectors), and Package 9 (Billing & Licensing) — `api/knowledge.py`, `api/documents.py`, `api/upload.py`, `api/search.py`, `api/chat.py`, `api/chat_sessions.py`, `api/conversation_summary.py`, `api/memory.py`, `api/memory_summary.py`, `api/users.py`, `api/organisations.py`, `api/permissions.py`, `api/connectors.py`, `api/connector_status.py`, `services/memory_service.py`, `services/auto_memory_service.py`, `services/worker_knowledge_service.py`, `services/connector_status_service.py`, `services/connectors/*.py`, and their schemas were confirmed against source, not taken secondhand from the architecture doc. For Package 9 specifically, the verification was a targeted, whole-repository grep (`licen|billing|plan|subscription|stripe|seat` — zero matches) plus reading every field on `models/organisation.py`/`models/user.py` and every one of the 39 routers in `main.py`, since there was no single file to point to — the finding *is* the absence. Everything about Packages 1–3's backend surface, and anything not listed below, still comes from `FRONTEND_ARCHITECTURE_V1.md` Part B (a review conducted when that document was written) plus references inside the implementation reports to a `FINAL_SECURITY_REMEDIATION.md` file that lives in the backend repo. See [[backend-status]] for the full summary and [[remediation-history]] for the security-hardening history as documented secondhand.

Headline facts worth keeping in working memory:

- Multi-tenant isolation (`organisation_id` scoping) is implemented and consistently enforced — solid.
- No CORS middleware, no refresh tokens, no logout/revocation endpoint, single-string role checks, no billing/plan data model at all.
- Five near-duplicate dashboard aggregate endpoints exist; the frontend has standardised on `GET /portal-dashboard/` as canonical (§C.6 of the architecture doc, confirmed followed in Package 2's implementation).
- Connectors (SharePoint/OneDrive/Teams) are hardcoded stubs, not real integrations.
- `DELETE /documents/{id}` and `POST /documents/reindex/{id}` have no role check at all (only `get_current_user`) — verified directly against `api/documents.py`. `POST /upload/` is similarly open to any authenticated org member, not admin-only.
- `POST /upload/`'s response (`{filename, status}`) never includes the created document's id — verified against `schemas/upload.py`. Anything building a post-upload redirect must account for this.
- **Real, live-reproduced defect:** `DELETE /documents/{id}` throws an unhandled `IntegrityError` (bare 500) when the document still has a `knowledge_permissions` row referencing it — `services/document_management_service.py#delete_document()` deletes the `Knowledge` row without first removing dependent permission rows. Since upload always creates an assignment, this affects the common case. See `KNOWLEDGE_IMPLEMENTATION_REPORT.md` §4/§10 for full repro and the fix needed.
- **`POST /chat/` silently creates a brand-new `ChatSession` on every single call and never returns its id** — verified directly against `services/chat_persistence_service.py#persist_chat()` (calls `create_session()` unconditionally) and confirmed live by sending a real chat message, then querying Postgres directly and finding the auto-created session with the right two messages, unreachable from the app itself. `POST /chat-sessions/{worker_id}` creates a *separate*, always-empty session with a real id — the two mechanisms don't connect. No specific conversation can be resumed or looked up from this frontend as a result. See `CHAT_IMPLEMENTATION_REPORT.md` §2 for the full mechanism.
- Ollama is real and working in this environment (`llama3`/`llama3.1` models present, `stream: False` hardcoded in `services/ollama_service.py` — confirmed no streaming exists), and a real completion was exercised end-to-end during Package 5's smoke test, correctly reflecting a worker's own configured instructions.
- **Neither `POST /memory/store` nor `GET /memory/{worker_id}`/`GET /memory-summary/` has any role check** (only `get_current_user` + worker-ownership) — verified directly against `api/memory.py`, and confirmed live with a non-admin account successfully adding a memory.
- **There is no update or delete endpoint for a memory anywhere in the backend** — only create and read exist. Verified by reading every route in `api/memory.py` and grepping the whole backend for `WorkerMemory` usage.
- **`services/auto_memory_service.py`'s trigger list is exactly 7 fixed, case-insensitive substring phrases** ("my preferred", "i prefer", "our preferred", "my vendor", "our vendor", "head office", "our office"), and it **stores the entire raw chat message verbatim** as the memory's content, not an extracted fact — verified both from source and live, by sending a real trigger-phrase message and confirming the resulting memory's content was the exact sentence sent.
- **`GET /users/` is admin-gated, not just `POST /users/`** — a real, backend-enforced boundary (unlike most list endpoints in this app), verified directly against `api/users.py`. `GET /organisations/` is likewise admin-gated and returns only `{id, name, slug}` — no plan/seat/billing field exists on the `organisations` table, confirming yet again there is no billing data model. `GET /permissions/` has no role check at all, asymmetric with the admin-only `POST /permissions/` on the same router — verified directly against `api/permissions.py`.
- **Real, live-reproduced defect:** `POST /permissions/` has no deduplication check, unlike `POST /worker-knowledge/assign`'s `assign_knowledge()` (which returns the existing row if one already exists) — calling it twice for the identical `(worker_id, knowledge_id)` pair creates two separate `KnowledgePermission` rows, confirmed directly in Postgres. A verified consequence: since the only delete path (`remove_knowledge()`) removes just one matching row, a single "Remove" click on a duplicated grant left one row — and the worker's access — intact. See `ADMIN_IMPLEMENTATION_REPORT.md` §2/§8/§10 for the full repro and the fix needed.
- **No user-role-change, deactivation, or delete endpoint exists** — confirmed by reading every route in `api/users.py`: create and list only.
- **Every connector endpoint (`GET /connector-status/`, `GET /connectors/{sharepoint,onedrive,teams}`) returns a hardcoded literal with no role check and no organisation-scoping at all** — verified directly against `api/connectors.py`/`api/connector_status.py`, and confirmed live: an admin and a non-admin account in the same freshly-created organisation both received the byte-for-byte identical response. `services/connectors/*.py`'s `SharePointConnector`/`OneDriveConnector`/`TeamsConnector` classes define real-looking `connect()`/`sync()` methods but are never instantiated or imported anywhere outside their own directory (confirmed by grepping the whole backend) — fully unreachable dead code. Even `BaseConnector.status()` (never overridden) would honestly report `"not_implemented"`, directly contradicting the "available" the live hardcoded endpoints claim.
- **Zero billing/licensing backend support exists at all — not even a stub.** Confirmed by grepping the entire backend for "licen|billing|plan|subscription|stripe|seat" (zero matches outside this frontend's own docs) and reading every field on `organisations`/`users` (name/slug only; no plan/tier/hosting/seat field anywhere). This is a stronger finding than Connectors' stubs — there is nothing to call, not merely a fake response. See `BILLING_AND_LICENSING_IMPLEMENTATION_REPORT.md` §2/§3 for the full, itemised list of backend work this would need.
- **A Next.js App Router rendering gap: a layout that renders a different tree instead of `{children}` does not stop the child route's own Server Component (and its real data fetches) from executing.** Found live during Package 9's smoke test: a non-admin's raw HTTP response for three new billing pages contained an unreferenced, real-data copy of admin-gated content in the React Server Component flight payload, even though the visibly-rendered page correctly showed only `app/portal/(protected)/admin/layout.js`'s restricted message. Fixed for Package 9's own three affected pages (each now checks the role itself before fetching); very likely also affects Package 7's pre-existing `/portal/admin/{users,organisation,permissions}` pages the same way, not yet fixed there. See `BILLING_AND_LICENSING_IMPLEMENTATION_REPORT.md` §9.

## 4. Commercial state

Editions and worker catalogue are **approved but not yet implemented in any billing/licensing system** — there is no `organisations.plan` column, no Stripe↔backend bridge, no license-file issuance mechanism. This is documented as the design target in [[commercial-model]], [[licensing-model-v1]] (approved 2026-08-15, ADR-011 — supersedes the original [[licensing-model]], which is marked superseded, not deleted; see [[licensing-changelog]]), [[pricing-model]], and [[product-editions]], and as the single longest-lead-time item in the roadmap ([[roadmap]] §Billing & Licensing). Package 9 has now built the full frontend UX this design target describes, against illustrative reference data (§2/§3) — the backend schema/endpoint work is the only thing separating that scaffold from a real feature, and is now the single blocking dependency for the rest of this roadmap (every other package has shipped). Separately, [[ux-vision]] (ADR-012) sets a Natural Language First / Wizard Second / Forms Last design-evaluation order — Package 9's three request wizards (renewal, worker pack, ownership transfer) are the first screens built directly against this rubric's Wizard tier, per §5 item 4's explicit instruction that human-approval-gated actions warrant a guided flow regardless of NL feasibility.

## 5. Open risks carried at all times

These are standing conditions, not one-time bugs — read them before making a decision that touches auth, billing, or connectors:

1. Frontend gating (role/plan checks in the UI) is presentation-only; the backend's `require_role` is the only real enforcement, and there is zero plan/seat enforcement anywhere yet.
2. Sovereign Edition ([[product-editions]]) requires hardware-bound, offline-capable licensing that doesn't exist in any form today — no license-file format, no signing key infrastructure, no validation code. This is greenfield work, not an extension of anything currently built.
3. The backend's "recent activity" ordering is not actually chronological (no timestamp columns) — cosmetic today, will mislead if surfaced as history-of-record for compliance or Licensing & Compliance Worker consumption later.
4. **No worker-update or worker-delete endpoint exists backend-side.** `EditWorkerForm.js` is fully editable but deliberately non-persisting (an honest "saving isn't available yet" notice on submit) — see `WORKERS_IMPLEMENTATION_REPORT.md` §8. This is a backend gap to track, not a frontend defect.
5. **`DELETE /documents/{id}` is broken for any document still assigned to a worker** — throws an unhandled FK-violation 500 instead of either cascading the delete or rejecting cleanly (see §3). Reproduced live during Package 4's smoke test; the frontend surfaces the resulting 500 as an inline error rather than masking it, but cannot fix the underlying defect from this repo. Needs a backend-side fix (`delete_document()` should remove the document's `knowledge_permissions` rows first, or the route should return a clear 409) before "delete a document" is reliably usable.
6. **No chat conversation can be resumed or looked up by the user who had it.** `POST /chat/` creates a new session every call and never returns its id (see §3) — this is the single highest-value backend fix identified so far for the actual product experience, since "have an ongoing conversation with a worker" is a core expected capability of an AI chat product. Needs `ChatRequest`/`ChatResponse` to carry a `session_id` and `persist_chat()` to reuse an existing session when one is given, rather than always creating a new one. See `CHAT_IMPLEMENTATION_REPORT.md` §2/§9.
7. **No memory can ever be corrected or removed once created.** Combined with auto-capture's plain substring-match trigger (no NLP/intent understanding — see §3), a message that innocently contains a trigger phrase for an unrelated reason ("is our office open Friday?") creates a permanent, unremovable memory row. Needs an update/delete endpoint backend-side; this frontend deliberately does not fake one. See `MEMORY_IMPLEMENTATION_REPORT.md` §2/§10.
8. **A knowledge↔worker permission grant can be duplicated, and "Remove" can silently fail to fully revoke access.** `POST /permissions/` has no dedup check (see §3); the only delete path removes one row at a time. This app's own Permissions UI prevents creating the duplicate through normal use, but cannot prevent it via a direct API call, and cannot guarantee one "Remove" click is complete if a duplicate already exists. Needs a backend-side fix — a dedup check on create (mirroring the already-correct `assign_knowledge()`), a unique DB constraint on `(worker_id, knowledge_id)`, or both. See `ADMIN_IMPLEMENTATION_REPORT.md` §2/§8/§10.
9. **No user-role-change, deactivation, or delete endpoint exists.** A mis-assigned admin role, or a user who should lose access, cannot be corrected from this app. See `ADMIN_IMPLEMENTATION_REPORT.md` §10.
10. **No password policy is enforced backend-side**, and `role` has no server-side enum — any string passes `UserCreate`'s validation; only this frontend's own form imposes a non-empty-password and admin/member convention. See `ADMIN_IMPLEMENTATION_REPORT.md` §2.
11. **Connectors are entirely non-functional and not organisation-scoped even in principle.** Every organisation and every user sees the identical hardcoded connector status; the connector class hierarchy that would implement real OAuth is unreachable dead code (see §3). Not a frontend gap — this frontend accurately represents that reality rather than building around it. See `CONNECTORS_IMPLEMENTATION_REPORT.md` §2/§9.
12. **Every screen in Package 9 (Billing & Licensing) except real usage counts and the real organisation identity shown in one wizard step is illustrative reference data, not a real licensing record.** This is the largest, most consequential gap in the entire product — nothing about tier, hosting model, licence status, expiry, or entitlement requests is real or persisted anywhere. See `BILLING_AND_LICENSING_IMPLEMENTATION_REPORT.md` §3 for the full, itemised backend-requirements list needed to change this, starting with an organisation-level licence record (the single prerequisite everything else in that list depends on).
13. **A layout that conditionally renders instead of `{children}` does not stop the hidden child route's own Server Component (and its data fetches) from executing** — found and fixed for Package 9's own three new pages during smoke testing, but very likely still true of Package 7's pre-existing `/portal/admin/{users,organisation,permissions}` pages, not yet fixed there. The visible page has never been wrong in either case; only the raw, unrendered HTTP response bytes carry the extra (own-organisation-scoped, not cross-tenant) data. See `BILLING_AND_LICENSING_IMPLEMENTATION_REPORT.md` §9.
