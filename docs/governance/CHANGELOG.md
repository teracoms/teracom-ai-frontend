## 2026-08-18 — Package Q (Commercial Provisioning & Entitlements) shipped

The highest-value follow-on wave identified after Package PQR: turns a completed sale into a fully provisioned customer environment, explicitly excluding billing engines/payment gateways. Discovered that `LicenceRequest`'s `worker_pack`/`tier_change`/`hosting_change` types were already validated as requiring the right payload fields but were never wired to actually do anything on staff approval, and that `services/entitlement_service.py#recompute_worker_limit()` had been dead code since Package B. Added `WorkerPackAddOn` (the +5/+10 quantity add-on, now real and accumulating correctly across purchases and across tier changes), wired `tier_change`/`hosting_change` to actually supersede a licence (reusing the unchanged `generate_licence()`), and built `services/worker_pack_provisioning_service.py` to close the gap `models/worker_pack.py`'s own docstring named as deferred since Package D: a customer can now provision every persona template in a Marketplace pack into real, entitlement-checked `Worker` rows in one atomic action — the first place `LICENSING_MODEL_V1.md` §4's "hard stop at the worker limit" policy is actually enforced anywhere in this backend (deliberately not retrofitted onto the pre-existing `POST /workers/` or `WorkerCreationRequest` paths — a stated scope boundary, not an oversight). A new `OrganisationOnboardingTask` model (deliberately separate from Package J's `CrmContact`-scoped `OnboardingTask`) seeds a 5-item welcome checklist on an organisation's first licence activation and appends a follow-up item per pack provisioned. Frontend: `WorkerPackWizard.js` now submits a real `POST /licensing/requests` (previously decorative — `WizardShell.js`'s `onSubmit` was awaited but had nowhere real to go); `RenewalWizard.js`/`OwnershipTransferWizard.js` deliberately left as-is, since both need real tier/hosting/licence data this package did not build. 10 new backend tests (200 total), 7 new frontend unit tests (294 total). Full detail: `docs/backend/PHASE_0_PACKAGE_Q_COMMERCIAL_PROVISIONING_AND_ENTITLEMENTS_IMPLEMENTATION_REPORT.md`.

**Why it mattered:** Packages G through PQR built an enormous amount of organisational-intelligence product surface, but a paying customer still had no real path from "sale approved" to "workforce provisioned" — the worker catalogue (Package D) and the entitlement/licensing engine (Packages A–C) existed side by side without ever being connected. This package is the connective tissue, and the first to make `LICENSING_MODEL_V1.md`'s worker-limit enforcement policy real anywhere in the product, even if only on one path so far.

## 2026-08-15 — Package 9 (Billing & Licensing) shipped as a frontend UX scaffold

`/portal/admin/billing` (Overview + Grace Period/Locked Mode previews), `/licence`, `/usage` (Capacity Monitoring), `/renewal`, `/worker-pack`, `/ownership-transfer` (three guided wizards), `/requests`. Grepping the entire backend for "licen|billing|plan|subscription|stripe|seat" before writing any code confirmed **zero billing/licensing backend support exists at all** — not even a stub, a stronger finding than Package 8's connector stubs. Built against a new, explicitly-labelled `lib/licensing/referenceLicence.js` reference-data module (not under `lib/api/`, since there is no backend endpoint to wrap) rather than building nothing — real backend data is used everywhere it genuinely exists (current worker/user/organisation counts via Packages 2/3/7, real organisation identity in the Ownership Transfer wizard), and reference data is used only where no real data exists at all, with every screen saying so explicitly. Applied the UX Vision rubric per screen: the three wizards landed on Wizard tier by direct governance instruction (human approval is mandatory regardless of NL feasibility); every other screen is a read-only display outside all three tiers, the same category Package 8's connector page landed in. Locked Mode is a preview only — it does not gate `/portal/**`, since no backend signal exists to drive that safely; the same "don't fabricate behaviour the backend can't back" discipline every prior package applied. **Found and fixed a real information-exposure bug during smoke testing**: a non-admin's raw HTTP response for three of the new pages contained an unreferenced, real-data copy of admin-gated content (own-org worker/user counts, own-org name) inside the React Server Component flight payload, even though the visibly-rendered page correctly showed only the restricted message — root-caused to a Next.js App Router behaviour (a layout rendering a different tree instead of `{children}` does not stop the child page's own Server Component, and its data fetches, from executing). Fixed for all three new pages by checking the role before making any real fetch; flagged as a carried-forward gap likely affecting Package 7's own admin pages the same way. 90 unit tests passing (8 new, zero new backend-calling functions). Full detail: `docs/frontend/IMPLEMENTATION_REPORTS/BILLING_AND_LICENSING_IMPLEMENTATION_REPORT.md`.

**Why it mattered:** completes every package in the original Part E roadmap; the first package built with no real backend surface to verify against at all, requiring a genuinely different approach (reference data, explicitly labelled) rather than the "verify then wire" discipline every prior package used; and the first package whose own smoke testing surfaced a real security-relevant finding in a *previously-shipped* package's shared layout pattern, not just in its own new code.

## 2026-08-15 — Package 8 (Knowledge Connectors) shipped

`/portal/knowledge/connectors` — SharePoint, OneDrive, and Microsoft Teams each rendered as a disabled "coming soon" card, integrated as a sub-page of the existing Knowledge section (a "Connectors" button on `/portal/knowledge`, no new top-level nav entry needed). Verified the actual backend source directly (`api/connectors.py`, `api/connector_status.py`, `services/connector_status_service.py`, `services/connectors/*.py`) before building, confirming every connector endpoint returns a hardcoded literal with no OAuth, no Microsoft Graph call, and — a new finding beyond what the architecture doc already stated — no organisation-scoping or role-gating at all: every org and every user gets the byte-for-byte identical response, confirmed live with both an admin and a non-admin account. Also found that `services/connectors/*.py`'s `SharePointConnector`/`OneDriveConnector`/`TeamsConnector` classes, which define real-looking `connect()`/`sync()` methods, are never instantiated or imported anywhere outside their own directory — fully unreachable dead code, and even `BaseConnector.status()` (never overridden) would honestly report `"not_implemented"`, directly contradicting the "available" the live hardcoded endpoints claim. Evaluated against the newly-approved `[[ux-vision]]` rubric (natural language → wizard → form) and recorded the outcome: this screen falls outside all three tiers, since no connector action exists anywhere in the backend to guide a user through. Zero new BFF proxy routes needed (purely read-only); 4 new CSS lines. 82 unit tests passing (1 new). Full detail: `docs/frontend/IMPLEMENTATION_REPORTS/CONNECTORS_IMPLEMENTATION_REPORT.md`.

**Why it mattered:** completes every package in `FRONTEND_ARCHITECTURE_V1.md`'s original Part E sequencing except Billing & Licensing, leaving exactly one package open going forward instead of two differently-blocked ones; also the first package explicitly evaluated against the new UX Vision rubric, recording a "none of the three tiers apply" outcome rather than defaulting to a form for convenience.

## 2026-08-15 — Licensing Model V1 and UX Vision approved (documentation only)

The project owner approved a full restructuring of the licensing/commercial model — Starter/Enterprise/Sovereign editions split into three tiers (Starter/Enterprise/**Platinum**, new) plus an independent hosting-model axis (Teracom Hosted / Dedicated Hosted / Customer Hosted (Sovereign)) — recorded in the new [[licensing-model-v1]], with full change detail in [[licensing-changelog]] and ADR-011 in [[architecture-decisions]]. [[commercial-model]] and [[product-editions]] were updated to match; the original [[licensing-model]] is marked superseded, not rewritten. Separately, the project owner approved a UX design philosophy — Natural Language First, Wizard Second, Forms Last — recorded in the new [[ux-vision]] and ADR-012. No application code was touched; see `docs/DOCUMENTATION_UPDATE_REPORT.md` for the full inventory of this documentation pass.

**Why it mattered:** the licensing lifecycle (renewal window, grace period, Locked Mode, hardware-bound licensing, human approval, appliance delivery, support tiers) now has concrete decided behaviour for the first time, giving the still-blocked backend billing-schema conversation ([[roadmap]] §9) real requirements to design against; and the UX vision gives future packages (8 onward) a stated design-evaluation order instead of defaulting to forms by default.

## 2026-08-15 — Package 7 (Administration) shipped

`/portal/admin` (landing/dashboard), `/portal/admin/users` (list + create), `/portal/admin/organisation` (read-only, reused from Package 2), `/portal/admin/permissions` (org-wide knowledge↔worker matrix). Added two BFF proxy routes and one shared `layout.js` gating the entire admin tree by role — the first package to use a nested layout for role-gating rather than repeating the check per page. Verified the actual backend source directly (`api/users.py`, `api/organisations.py`, `api/permissions.py`, `services/worker_knowledge_service.py`) before building, which surfaced a real, live-reproduced bug: `POST /permissions/` has no deduplication check (unlike the equivalent `assign_knowledge()` used elsewhere), so calling it twice for the same worker+document pair creates two separate database rows — confirmed directly in Postgres. A further consequence was also verified live: because the only delete path removes just one matching row, a single "Remove" click on a duplicated grant left the worker's access silently intact. The admin UI's own assign picker excludes already-granted pairs so normal use can't create this duplicate, but the underlying backend gap remains open. Zero new CSS lines needed — the smallest footprint of any package so far. 81 unit tests passing (10 new). Full detail: `docs/frontend/IMPLEMENTATION_REPORTS/ADMIN_IMPLEMENTATION_REPORT.md`.

**Why it mattered:** fourth consecutive package where reading the actual backend source before coding found a real, previously-undocumented defect — and the first where that defect had a security-relevant consequence (an admin believing access was revoked when it wasn't) rather than just a broken or missing feature; also the first package to introduce role-based (not just session-based) route-group gating as a reusable pattern.

## 2026-08-15 — Package 6 (Memory) shipped

`/portal/memory` (worker-grouped overview with cross-worker search), `/portal/memory/:workerId` (per-worker view + manual "add a memory" form), `/portal/memory/:workerId/:memoryId` (read-only detail). Added one BFF proxy route (`app/api/portal/memory/route.js`) for the manual-entry form. Verified the actual backend source directly (`api/memory.py`, `services/memory_service.py`, `services/auto_memory_service.py`, `models/worker_memory.py`) before building, confirming §C.10's description exactly (no org-wide memory endpoint, `memory_type` always `"fact"`) while also surfacing new facts: neither memory endpoint is role-gated, there is no update/delete endpoint for a memory at all, the auto-capture trigger list is exactly 7 fixed substring phrases, and — verified live, not just from source — auto-captured memories store the *entire raw chat message*, not an extracted fact. Cross-linked the existing Worker detail page's (Package 3) read-only Memory section to the new per-worker page. Smallest CSS footprint of any package so far (+4 lines) — nearly everything reused pre-existing classes. 71 unit tests passing (5 new). Full detail: `docs/frontend/IMPLEMENTATION_REPORTS/MEMORY_IMPLEMENTATION_REPORT.md`.

**Why it mattered:** third consecutive package (after Knowledge and Chat) where reading the actual backend source before coding shaped real UI decisions — no edit/delete affordance was built because none can be backed, and content truncation was designed around memories being potentially full sentences, not short facts, because that was verified live rather than assumed; also the first package to close a loop by linking back into a prior package's existing page rather than only building forward.

## 2026-08-15 — Package 5 (Chat) shipped

`/portal/chat` (worker picker), `/portal/chat/:workerId` (live composer + in-page thread), `/portal/chat/:workerId/:sessionId` (read-only session detail). Added two BFF proxy routes (`app/api/portal/chat/*`) for sending a message and starting a tracked session. Verified the actual backend source directly (`api/chat.py`, `services/chat_persistence_service.py`, `services/chat_session_service.py`) before building, which surfaced the package's central finding: `POST /chat/` silently creates a brand-new `ChatSession` on every call and never returns its id, so no specific conversation can ever be resumed or looked up from this app — confirmed live by sending a real message, then querying Postgres directly and finding a second, auto-created session the app itself has no way to discover. Confirmed via source (`services/ollama_service.py`'s hardcoded `"stream": False`) that no streaming exists, so the composer uses a blocking loading indicator instead (~12s observed for a real completion in testing). Designed around this honestly: live chat is client-side-only per page load, and a separate, fully-working "start a tracked session" flow exercises the real per-session endpoints without pretending the two are connected. 66 unit tests passing (7 new). Full detail: `docs/frontend/IMPLEMENTATION_REPORTS/CHAT_IMPLEMENTATION_REPORT.md`.

**Why it mattered:** first package where a real (non-mocked) LLM completion was exercised end-to-end, correctly reflecting a worker's own configured instructions; second consecutive package (after Knowledge) where reading the actual backend source before coding prevented building a feature the backend can't actually support (a resumable conversation), rather than discovering the gap after the UI promised it.

## 2026-08-15 — Package 4 (Knowledge) shipped

`/portal/knowledge` (list, stat chips, semantic search, search/filter), `/portal/knowledge/upload` (multipart upload form + upload-activity panel), `/portal/knowledge/:documentId` (content, read-only assigned-workers reverse lookup, reindex/delete). Added four BFF proxy routes (`app/api/portal/knowledge/*`), including the app's first multipart-body proxy — required extending `lib/api/client.js#backendFetch` to send `FormData` as-is instead of always JSON-encoding. Verified the actual `teracom-ai-backend` source directly (not just the architecture doc) before building against it, which surfaced two real backend facts the doc doesn't state: `POST /upload/` returns no document id (so post-upload can't redirect to the new document), and `DELETE /documents/{id}`/`POST /documents/reindex/{id}` are not role-gated at all backend-side. Found and characterized (not fixed — backend repo) a real defect: deleting a document that's still assigned to a worker throws an unhandled FK-violation 500, since `delete_document()` doesn't clean up `knowledge_permissions` rows first. 59 unit tests passing (14 new). Full detail: `docs/frontend/IMPLEMENTATION_REPORTS/KNOWLEDGE_IMPLEMENTATION_REPORT.md`.

**Why it mattered:** first package where documents actually exist in the org for chat context to draw on ahead of Package 5 (Chat); first package to require reading the real backend source before the architecture doc's description because a response shape (`POST /upload/`) mattered enough to get wrong; first real backend bug this project has found and documented via live smoke testing rather than code review alone.
