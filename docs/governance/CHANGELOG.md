## 2026-08-19 — Wave 1, Workstream 5 (Licensing and Entitlement Architecture) shipped

A real, queryable `Plan` entity (`code`, `display_name`, `worker_limit`, `user_limit`, `organisation_limit`, `monthly_price_cents` — nullable, real pricing not yet decided — `is_active`), seeded to mirror `services/entitlement_service.py#_TIER_LIMITS` exactly (verified by a new drift-guard test). `Licence` gained an additive `plan_id` FK, populated for every new licence issued going forward (`generate_licence()`) and backfilled for any pre-existing licence via the new migration (`9d4b6f1e2c7a`) — verified both by the standard migration-correctness suite and a dedicated test that downgrades one revision, inserts a raw pre-migration licence row, upgrades back to head, and confirms the backfill resolved the right plan. A new `LicenceBillingReference` side table (all fields nullable, all currently unpopulated) is prepared for a future Commerce-to-Licensing Lifecycle Automation service, without needing its own later migration. New `GET /licensing/plans` endpoint. Investigation before implementation found `capability_allowed_for_tier()` has 13 real call sites (not seven, the source plan's own working estimate), all funnelling through one chokepoint (`get_organisation_current_tier()`) — deliberately left reading `Licence.tier` directly, unchanged, since converting all 13+ to read through `plan_id` in this same pass would have been a materially larger, higher-risk change than this foundation-only workstream's own "zero behaviour change" scope allowed. No new audit table was created — `LicensingAuditLog` already existed and already covers this. Backend: 277/277 tests passing (6 new). Frontend: no changes needed, 302/302 passing. Full detail: `docs/backend/WAVE1_LICENSING_ENTITLEMENT_ARCHITECTURE_IMPLEMENTATION_REPORT.md`, ADR-032.

**Why it mattered:** lays the schema foundation the later, larger Commerce-to-Licensing Lifecycle Automation service (amended `COMMERCIAL_READINESS_ASSESSMENT.md` §9) needs to build into, without attempting that larger, riskier build in the same pass — and is a clean example of this wave's own recurring discipline: investigate the real scope of a change before committing to an approach, and recognise an existing mechanism (`LicensingAuditLog`) rather than duplicating it.

## 2026-08-19 — Wave 1, Workstream 4 (META1 - Metadata Foundation) shipped

The first genuinely new capability in this wave (Workstreams 1-3 were all bug fixes) — a deliberately narrow classification layer for Knowledge documents, built ahead of the Organisation Knowledge Graph/Document Lifecycle Governance/Organisational Search packages it exists to serve, per `KNOW1_ASSESSMENT.md` §6's own reasoning that retrofitting one later would be materially more expensive. `Knowledge` gained two new nullable columns (`document_type`, `sensitivity_level` — five and three allowed values respectively) and a `tags` relationship to a new `knowledge_tags` table (a real join table with a real index on `tag`, not a JSONB array, specifically so a future "all documents tagged X" query — the Knowledge Graph's own named need — can use it). A new `services/metadata_service.py` is the one place these fields should be read or written, validating regardless of caller (API route or a future internal service) rather than only at the Pydantic schema boundary. New API surface: `POST /knowledge/` accepts all three fields as optional (a document created without them is simply unclassified, no backfill required), plus new `GET`/`PATCH /knowledge/{id}/metadata` endpoints (admin-only write, matching the existing Knowledge-write convention; cross-organisation isolation enforced via the existing `get_owned_knowledge()` check). New migration `7a2c9e4f1b8d`, applied to the real dev database and verified via the existing migration-correctness tests. Backend: 271/271 tests passing (11 new). Frontend: no changes — classification remains admin/API-only in this v1, with a UI deferred until a real consumer (Knowledge Graph, Document Lifecycle Governance, or Organisational Search) exists to justify one; 302/302 passing, unaffected. Full detail: `docs/backend/WAVE1_META1_METADATA_FOUNDATION_IMPLEMENTATION_REPORT.md`, ADR-031.

**Why it mattered:** this is the foundation `teracom-ai-docs`' own `KNOW1_ASSESSMENT.md` identified as the single highest-leverage sequencing correction versus the original roadmap — pulled forward specifically to avoid the "build the mechanism once, not many times" mistake this project's own governance discipline (SD-002/SD-003 in the strategy docs, echoed by this file's own ADR-028) has already named and corrected once before.

## 2026-08-19 — Wave 1, Workstream 3 (Password Reset Completion) shipped

Fixed a real defect independent of Workstream 2's SMTP-credential question: `services/password_reset_service.py#request_password_reset()` and `services/portal_contact_password_reset_service.py#request_portal_contact_password_reset()` both generated a real reset token and then discarded it — the token never reached the outbound email at all, so the password-reset email always instructed the recipient to "use the link your administrator provides" with no link ever present, on both identity planes, regardless of whether SMTP was configured. Both service functions now build a real reset URL immediately after generating the token (`f"{FRONTEND_BASE_URL}/portal/reset-password?token=..."` and the `/customer-portal/...` equivalent) and thread it through the shared `notify_password_reset_requested()` (extended with a new `reset_url` parameter) into a rewritten `_password_reset_requested` email template that renders a real, working link. A new `FRONTEND_BASE_URL` backend config setting was added — the backend had never needed to construct a link back to the frontend before, and no existing config value could be reused; it mirrors the frontend's own `NEXT_PUBLIC_SITE_URL` naming. The frontend's `/portal/reset-password` and `/customer-portal/reset-password` pages already correctly read a `?token=` parameter and call the real backend confirm endpoints — confirmed by direct inspection, not assumed, and needed no changes. Backend: 260/260 tests passing (2 new, one per identity plane, each asserting the persisted `EmailMessage.template_context` and the rendered HTML/text body both contain the real reset URL — not just that the notification function was called). Frontend: unaffected, 302/302 passing. Full detail: `docs/backend/WAVE1_PASSWORD_RESET_COMPLETION_IMPLEMENTATION_REPORT.md`, ADR-030.

**Why it mattered:** closes the third of four Day-0 internal-pilot blockers identified in `INTERNAL_PILOT_READINESS_ASSESSMENT.md`, and is the clearest example yet in this wave of a defect that would have survived even a fully-configured SMTP credential — the email content itself was broken, a distinct failure mode from "nowhere to send it," worth fixing as its own defect rather than assuming it would resolve itself once Workstream 2 landed.

## 2026-08-19 — Wave 1, Workstream 2 (SMTP Completion) shipped

Added a full activation runbook (`docs/operations/PRODUCTION_RUNBOOK.md` §9) with exact `.env` values and post-activation verification steps. Real delivery remains unconfigured in this environment — provisioning an external mailbox/relay account requires access outside this session's scope; this is now purely a configuration step. Backend: 258/258 tests passing (1 new). Frontend: unaffected, 302/302 passing. Full detail: `docs/backend/WAVE1_SMTP_COMPLETION_IMPLEMENTATION_REPORT.md`, ADR-029.

**Why it mattered:** closes the second of four Day-0 internal-pilot blockers identified in `INTERNAL_PILOT_READINESS_ASSESSMENT.md`, and demonstrates the correct handling of a workstream whose remaining step is genuinely outside engineering's authority — proving everything provable, documenting the exact remaining step precisely, and not fabricating a credential or a result to manufacture the appearance of completion.

## 2026-08-19 — Package OPS1 (Production Runtime and Service Management) shipped

Operational-only package, no application/UX changes: both services now run as supervised, boot-persistent systemd units instead of ad hoc foreground `npm run dev`/`uvicorn` commands in SSH terminals — the direct root cause of the same day's earlier "why is port 3000 occupied" investigation. No root/sudo was available this session (`sudo -n true` failed); `loginctl enable-linger` succeeded without it, making **user-level** systemd units (`systemctl --user`) a fully viable substitute for boot-start and crash-recovery, documented as a limitation with an explicit migration path to system-level units if root access is obtained later. `frontend/package.json`'s `start` script now pins `next start -p 3000` so the port is locked at the source, not just in the unit file. Backend now binds `127.0.0.1:8000` only (was `0.0.0.0`) — hardened, since the only consumer is the co-located frontend. Both `Restart=on-failure` policies were tested for real: each service's actual main PID was `kill -9`'d and confirmed to auto-recover with a new PID. Boot-enablement (`is-enabled`, `default.target.wants` symlinks, `Linger=yes`) was fully verified; an actual reboot was deliberately not performed without asking first, since this is a shared host with other active sessions. Full detail: `docs/backend/PACKAGE_OPS1_PRODUCTION_RUNTIME_AND_SERVICE_MANAGEMENT_IMPLEMENTATION_REPORT.md` and `docs/operations/PRODUCTION_RUNBOOK.md`.

**Why it mattered:** every prior package in this series ran its own live verification by hand-starting both services in a terminal and killing them again afterward — convenient for iterative development, but never something a real production deployment should rely on. This is the first package to treat "the app stays up" as its own deliverable rather than a byproduct of someone's terminal staying open.
