# Architecture Decisions

**Format:** lightweight ADR log — each entry is a decision that was actually made and shipped (or explicitly approved for future work), with the reasoning behind it, so a future worker doesn't accidentally re-litigate or reverse it without knowing why it exists. New decisions are **appended**, never rewritten in place — if a decision is superseded, add a new entry that says so and leave the old one for history.

See [[frontend-architecture]] for the full design document these are drawn from, and [[worker-operating-standards]] for when a worker is required to add a new ADR here.

## ADR-001 — Extend, don't redesign, the existing marketing site

**Status:** Adopted. **Source:** `FRONTEND_ARCHITECTURE_V1.md` Part C, confirmed followed in both implementation packages.

The authenticated product area is built entirely additively under `/portal/**`. Nothing in `/`, `/securityos-ai`, `/store`, `/checkout/**`, `app/layout.js`, `components/Header.js`/`Footer.js`, or the design tokens in `globals.css` is redesigned or restyled. New screens reuse the existing container width, section rhythm, button/card/badge classes, and colour tokens.

**Why:** the marketing site is a lean, deliberately-scoped asset with no legacy debt — extending it costs less and risks less than parallel-building a new design system, and keeps the authenticated app visually part of the same product family.

**How to apply:** any new screen must be checked against `globals.css`'s existing token set before adding a new CSS custom property or class family. New tokens are a last resort, not a first move.

## ADR-002 — BFF (backend-for-frontend) pattern; browser never talks to the backend directly

**Status:** Adopted and shipped (Package 1). **Source:** `FRONTEND_ARCHITECTURE_V1.md` §C.4, `AUTHENTICATION_IMPLEMENTATION_REPORT.md` §2.

All backend calls are made server-side, from Next.js Route Handlers or Server Components, never from client-side `fetch`. The browser only ever talks to the Next.js app's own origin.

**Why:** two independent backend constraints forced this — (1) `POST /auth/login` reads credentials as query parameters, not a JSON body, so a server-side proxy is the only way to keep credentials out of the browser's visible URL/network tab; (2) the backend has no CORS middleware at all, so direct browser→backend calls would simply fail cross-origin. The BFF pattern solves both at once without waiting on backend fixes.

**How to apply:** every new domain module under `lib/api/*` is server-only. If a client component needs live data, it calls a same-origin `app/api/portal/*` Route Handler that proxies server-side — it never calls `BACKEND_API_URL` directly. `BACKEND_API_URL` must never carry a `NEXT_PUBLIC_` prefix.

## ADR-003 — Session stored as an httpOnly cookie, never localStorage or client-visible state

**Status:** Adopted and shipped (Package 1). **Source:** `AUTHENTICATION_IMPLEMENTATION_REPORT.md` §2.

The backend's JWT is set as an `httpOnly`, `Secure`, `SameSite=Lax` cookie (`teracom_session`) by `app/api/auth/login/route.js`. It is never written to `document.cookie`, never returned in a client-visible response body, never placed in `localStorage`/`sessionStorage`.

**Why:** the backend issues a bare JWT with no refresh token and no revocation endpoint — if it leaks via XSS, it's valid until natural expiry with no way to invalidate it early. An httpOnly cookie is the only realistic mitigation available given that backend constraint.

**How to apply:** never add a code path that exposes the raw session token to client-side JavaScript, even for convenience (e.g. "just read it in a client component to check expiry"). Client components get identity via `AuthProvider`/`useAuth()`, seeded server-side, not via the raw token.

## ADR-004 — Two-layer route guard: Edge middleware (presence-only) + Server Component (authoritative)

**Status:** Adopted and shipped (Package 1). **Source:** `AUTHENTICATION_IMPLEMENTATION_REPORT.md` §2, §6.4.

`middleware.js` checks only that the session cookie is *present* before allowing a request under `/portal/**` to proceed — it does not verify the JWT signature or expiry. The authoritative check is `app/portal/(protected)/layout.js`, a Server Component that calls the backend's own `GET /auth/me`, which naturally rejects expired tokens and deleted users.

**Why:** verifying the JWT at the Edge would require either bundling a JWT library into the Edge runtime or shipping the backend's signing secret into the frontend's environment — both add real risk for a check that is advisory defense-in-depth, not the actual security boundary. Delegating the authoritative check to a real backend call means the frontend never reimplements JWT verification logic that could drift from the backend's own.

**How to apply:** never treat a middleware pass as proof of a valid session in any new code. Any screen or action with real consequences must go through a path that calls the backend and can be rejected by it. See ADR-006 (presentation-only gating) for the corollary.

## ADR-005 — Route groups separate public and protected `/portal` pages

**Status:** Adopted and shipped (Package 1). **Source:** `AUTHENTICATION_IMPLEMENTATION_REPORT.md` §2.

`app/portal/(public)/login/` and `app/portal/(protected)/*` are separate Next.js route groups, each with its own layout, rather than one shared guarded layout with conditional rendering.

**Why:** avoids a redirect loop between "am I logged in" and "show login form" and lets each group own the right `AuthProvider` seed (or none) without a double backend call per request.

**How to apply:** any new top-level auth state (e.g. a future "account locked" or "org suspended" state) should get its own route group rather than a conditional branch inside an existing layout, if it needs materially different chrome or guard behaviour.

## ADR-006 — Frontend role/plan gating is presentation-only, never a security boundary

**Status:** Adopted, standing policy. **Source:** `FRONTEND_ARCHITECTURE_V1.md` §C.5, restated in §C.12.5.

Hiding admin nav items for non-admins, or warning at a seat limit, is UI convenience only. The backend's `require_role`/`get_owned_*` checks are the only real enforcement, and today there is **no** plan/seat enforcement at all on the backend.

**Why:** the backend's role check is exact-string-equality with no hierarchy, and plan/seat limits don't exist server-side yet. Treating any frontend check as a security boundary would be actively false.

**How to apply:** never skip or soften a backend authorization call because "the UI already checked this." Every gated action must still hit the real endpoint and handle its 403/limit response. This is a permanent policy, not a placeholder to remove later — see [[security-standards]].

## ADR-007 — One canonical backend call per screen, ignoring redundant near-duplicate endpoints

**Status:** Adopted and shipped (Package 2). **Source:** `FRONTEND_ARCHITECTURE_V1.md` §C.6, `DASHBOARD_IMPLEMENTATION_REPORT.md` §2.

The backend exposes five-plus endpoints returning the same shape of organisation counts (`/dashboard/`, `/portal-dashboard/`, `/platform/summary`, `/system/overview`, `/stats/platform`). The dashboard calls only `GET /portal-dashboard/`, `GET /activity/`, and `GET /analytics/chat` — the other endpoints are never called.

**Why:** calling all of them would be pure waste (identical data, extra requests) and would make it ambiguous which one is "the" source of truth if they ever drift apart. Picking one canonical caller per screen keeps the frontend simple and gives the backend team a clear signal about which endpoints are actually load-bearing versus safe to deprecate.

**How to apply:** before wiring a new screen to a backend aggregate/summary endpoint, check whether an equivalent endpoint is already designated canonical elsewhere in this doc or in `frontend-architecture`. Don't add a second caller of the same underlying data shape without recording why here.

## ADR-008 — Per-section resilience via `Promise.allSettled`, not one page-level try/catch

**Status:** Adopted and shipped (Package 2). **Source:** `DASHBOARD_IMPLEMENTATION_REPORT.md` §4.

Independent backend calls on the same page (e.g. the dashboard's four calls) are fired concurrently and resolved individually via `lib/api/results.js#settle()`. One endpoint failing renders one inline error banner in its own section; it does not take down sections fed by other endpoints.

**Why:** the backend calls genuinely are independent (different endpoints, different failure modes — e.g. `/organisations/` is admin-gated and expected to 403 for most users) — coupling their failure handling would turn an expected, benign 403 into a page-wide error state.

**How to apply:** any screen making more than one independent backend call should use `settle()`/`errorMessage()`/`isForbidden()` from `lib/api/results.js` rather than a single wrapping try/catch, unless the calls are genuinely dependent on each other's success.

## ADR-009 — Sovereign Edition requires a fully separate, hardware-bound licensing architecture — no perpetual licences

**Status:** Approved (commercial decision), **not yet designed or built**. **Source:** user-approved commercial decisions, 2026-08-15.

Sovereign Edition is customer-hosted (backend runs on customer infrastructure, not Teracom's), with a signed, encrypted licence file bound to customer hardware, validated offline (no phone-home requirement), and time-bound (no perpetual licences are ever issued, even for Sovereign).

**Why:** customer-hosted deployment means Teracom cannot rely on a central server to enforce entitlement the way Starter/Enterprise do — the enforcement has to travel with the deployment. "No perpetual licences" is a deliberate commercial constraint to preserve renewal revenue and force periodic contact even with offline-capable customers.

**How to apply:** this is a placeholder decision, not an implementation — see [[licensing-model]] for the fuller design questions this raises (signing key custody, licence file format, hardware-binding mechanism, renewal/grace-period behaviour) that remain **open** and must be resolved by a Licensing & Compliance Worker or human before any Sovereign Edition build work starts. Do not begin implementation from this ADR alone.

## ADR-010 — Billing/licensing is out of scope for the frontend alone; requires backend schema work first

**Status:** Standing constraint, carried from `FRONTEND_ARCHITECTURE_V1.md` §C.12/§D/§E.

There is no `plan`/`status`/`seat_limit`/`stripe_customer_id` concept anywhere in the backend's data model today. The frontend cannot build a real billing/entitlement screen until the backend adds this schema and the corresponding endpoints.

**Why:** Stripe (payment) and the AI backend's organisation model (entitlement) are two disconnected systems today; a webhook-based sync point is the intended bridge, but the backend side of that bridge doesn't exist.

**How to apply:** any worker picking up billing/licensing work must start the backend schema conversation before writing frontend UI for it — see [[roadmap]] §9, which explicitly calls this out as the highest-lead-time item that should start in parallel with Package 1, not be sequenced last.

## ADR-011 — Licensing Model V1 approved: tiers restructured, hosting model decoupled from tier

**Status:** Approved (commercial decision); licensing lifecycle mostly decided, some mechanism-level questions remain open. **Source:** user-approved commercial decisions, 2026-08-15.

The three-edition model (Starter / Enterprise / Sovereign, where hosting was baked into the edition) is replaced by two independent axes: a **product tier** (Starter — 5 workers/10 users/1 org; Enterprise — 30 workers/Licensed User Count/up to 5 orgs; Platinum — 50 workers/Licensed User Count/up to 30 orgs) and a **hosting model** (Teracom Hosted, Dedicated Hosted, Customer Hosted (Sovereign)), selected independently. Also decided in the same pass: additional worker packs (+5/+10), a hardware fingerprint for hardware-bound licensing (VM UUID + Disk UUID + TPM where available), a mandatory human-approval step for licensing actions, an ownership-transfer workflow (allowed, human-approved), a renewal window (up to 90 days before expiry), a 30-day grace period with explicitly allowed actions, a terminal Locked Mode state after the grace period, an appliance delivery model (compiled application + signed licence + upgrade packages + configuration — no source/file access), and a two-tier support model (Teracom Support Worker, then human escalation).

**Why:** decoupling hosting location from commercial tier is more flexible than baking a single "Sovereign" edition around one hosting choice, and it gives the backend billing-schema conversation (ADR-010) concrete lifecycle requirements (renewal window, grace period, Locked Mode) to build against instead of an open question list.

**How to apply:** this supersedes the "Sovereign is a separate edition" framing in ADR-009 and the corresponding sections of [[product-editions]] and [[commercial-model]], both updated in place to match. ADR-009 is left unedited for history (append-only) — read it alongside this entry, not as the current model. [[licensing-model-v1]] is the new source of record; the original [[licensing-model]] draft is superseded (see its updated header) but its still-open items (signing key custody, licence file format, clock-tampering resistance, revocation) remain genuinely unresolved — see [[licensing-model-v1]] §19 for the consolidated list, including new open items this pass introduced (tier × hosting-model availability, upgrade/downgrade mechanics, the Partner/MSP model, and whether Tier 1 support consumes a worker seat). Do not begin build work on any item in that list without treating it as open.

## ADR-012 — UX principle adopted: Natural Language First, Wizard Second, Forms Last

**Status:** Approved (design direction), 2026-08-15. Roadmap/priority-ordering detail is proposed, not yet binding. **Source:** user-approved UX direction, 2026-08-15.

New screen and interaction design should be evaluated in this order of preference: (1) can the task be accomplished by asking a worker in natural language, (2) if not, can it be a short guided wizard, (3) a traditional static form is the last resort, reserved for bulk/tabular data, repeated power-user configuration, or precise/auditable input.

**Why:** Teracom AI's core product unit is a conversational Worker persona, and chat is already the platform's native, shipped interaction mode (Package 5) — administrative UI should default toward that same interaction model where feasible rather than defaulting to a second, disconnected forms/tables paradigm for everything that isn't chat.

**How to apply:** see [[ux-vision]] for the full philosophy, wizard strategy, a proposed priority list of existing form-first flows to revisit, and a design-evaluation rubric. This governs *new* screen design from this point forward — Packages 1–7 are not retroactively re-scoped by this ADR. Any new screen's implementation report should record which of the three tiers (NL / Wizard / Form) it landed on and why, per [[ux-vision]] §6.

## ADR-013 — Executive governance model adopted for the Department Head layer

**Status:** Approved (user-confirmed design decision), 2026-08-17. **Source:** user-approved design decisions during Phase 0 Package I planning.

A Department Head is an existing Worker referenced by a new `Department.head_worker_id` column — not a new entity — and the six recommended executive roles (CTO, CFO, Head of Sales, Head of Marketing, Head of Operations, Head of Customer Success) are a documented reference catalogue, never auto-created or bootstrapped by any endpoint: an admin creates every department, worker, and headship assignment manually, one action at a time. Direct communication between two Department Heads is a new, dedicated, auditable endpoint (`POST /department-heads/consult`) that reuses Package F's existing consult-then-synthesise mechanism unchanged, rather than either duplicating it or silently reusing the generic endpoint with no access restriction. "Department-owned worker management" is visibility plus Package H's existing admin-only reassignment path, not a new request/approval workflow — the pre-existing `require_role("admin")` gate on `POST /workers/` already satisfies "human approval for new worker creation." The target hierarchy's "Orchestrator" node is the existing CTO Orchestration mechanism (Package G/H), not a new worker or entity above CTO.

**Why:** worker creation and organisational restructuring already require human/admin action in this codebase — Department Heads are structural, not exempt from that. Full visibility into every organisational change matters more than convenience here, and inventing a new top-level "Orchestrator" entity or a parallel worker-creation-approval workflow would duplicate mechanisms this project already has working, tested equivalents for.

**How to apply:** see [[department-head-layer]] for the full model (the six roles, the governance-rule-by-governance-rule status table, and how this integrates with CTO Orchestration and department memory), and `PHASE_0_PACKAGE_I_DEPARTMENT_HEAD_IMPLEMENTATION_REPORT.md`/`DEPARTMENT_HEAD_IMPLEMENTATION_REPORT.md` for full implementation detail. Financial commitments, contracts, and customer pricing decisions remain explicitly not applicable to gate in code — no such capability exists anywhere in this backend (see ADR-010's billing-schema gap, still open).

## ADR-014 — Sales & Customer Success Platform: one contact entity, three separate approval entities, no real CRM sync

**Status:** Approved (user-confirmed design decisions), 2026-08-17. **Source:** user-approved design decisions during Phase 0 Package J planning.

A `CrmContact` is tracked on one row for its whole life (`stage`: prospect → lead → customer), not copied across separate Prospect/Lead/Customer tables — the same "reuse one entity, add a field" preference ADR-013 already applied to Department Heads. `Proposal`, `Quote`, and `Contract` are three separate tables, each with its own submit → admin-decide lifecycle (mirroring the existing `LicenceRequest` submit/decide pattern, but decided by the **organisation's own admin**, not Teracom staff, since this is the customer's own pipeline) — not one entity with more states, so a contract can be revisited without re-litigating the original proposal's approval. Only proposal *content* may be AI-drafted (gated by a new `sales_intelligence` capability, Enterprise+); quotes and contracts are always human-entered, since a made-up number is a materially different risk from a made-up paragraph of prose. A new nullable `Department.function` column (`"sales"` | `"customer_success"` | `null`) lets the executive dashboard identify the right department reliably. The CRM connector abstraction layer (objective #8) is cosmetic, mirroring Package 8's Connectors precedent exactly — never wired to anything real.

**Governance mapping:** "human approval for financial commitments" is satisfied by Quote/Contract's own approval gate (their `amount` field is part of the same gate) — no fourth, separate financial-commitment entity was built. "Human contact remains part of customer acquisition" is satisfied trivially: no outbound email/SMS/contact-automation capability exists anywhere in this backend, in this package or any prior one, so no code path could contact a prospect without a human.

**Why:** matches this project's established preference for minimal schema and for mapping a governance rule to an already-covered mechanism rather than building a redundant one, and keeps a materially higher-risk capability (AI-authored financial figures) out of scope entirely rather than half-building a safeguard around it.

**How to apply:** see `PHASE_0_PACKAGE_J_SALES_AND_CUSTOMER_SUCCESS_IMPLEMENTATION_REPORT.md` (backend) and `SALES_AND_CUSTOMER_SUCCESS_IMPLEMENTATION_REPORT.md` (frontend) for full implementation detail. [[sales-manager-worker]] and [[customer-success-manager-worker]] are this package's operational personas — distinct from [[head-of-sales-worker]]/[[head-of-customer-success-worker]] (Package I's advisory-only Department Head personas).

## ADR-015 — Marketing & Media Platform: retrofit Head of Marketing, a new three-tier pipeline pattern, and an originated content-publishing governance rule

**Status:** Approved (user-confirmed design decisions), 2026-08-17. **Source:** user-approved design decisions during Phase 0 Package K planning.

Unlike Head of Sales/Head of Customer Success (ADR-013), which got dedicated advisory-only executive docs before Package J built their operational counterparts, "Head of Marketing" was never split from Marketing Manager Worker's own catalogue entry — that persona has always been documented as both the recommended executive role and the one directing marketing strategy. Package K **retrofits** this existing persona with the campaign/dashboard/governance mechanics it now operates through, rather than splitting out a second, near-duplicate executive doc. A `Campaign` is the container that starts a genuinely new **three-tier** pipeline for this catalogue — Marketing Manager (direction) → Content Producer (content execution) → Video Producer (video execution) — where Video Producer's brief comes from an *approved* Content Producer output (`VideoAsset.content_piece_id`, mirrors `Quote.proposal_id`'s optional-chaining shape), not from Marketing Manager directly; every prior split in this catalogue (CTO/Developer, Sales, Customer Success) is two-tier. `ContentPiece`/`VideoAsset` share `Proposal`'s submit → admin-decide shape exactly. A new dedicated `MediaCentreItem` model (not an extension of Package 4's Knowledge/Document model — a media asset is publication-lifecycle-oriented, not permission/embedding-oriented) is created only from an *approved* content piece or video asset, and only advances from `"ready"` to `"published"` via a further explicit, admin-only action. The YouTube connector (objective #9) is cosmetic, mirroring Package 8's/Package J's connector precedent exactly — never wired to anything real. `Campaign`/`ContentPiece`/`VideoAsset`/`MediaCentreItem` are all organisation-scoped, matching `CrmContact`'s precedent, not department-scoped.

**Governance mapping — this package originates a new rule, unlike ADR-013/014 which mapped onto existing ones:** no existing governance rule in this project covers content or media publishing (confirmed absent by a repo-wide search during planning). Package K originates: "human approval required before content or video is publishable (the submit → admin-decide gate on `ContentPiece`/`VideoAsset`), and a further explicit admin action is required before a Media Centre item is actually marked published." Only content and script *drafting* get AI-assist (a new `marketing_intelligence` capability, Enterprise+, gating `POST /content/draft` and `POST /videos/draft-script`) — submitting, deciding, publishing, and marking-published are always explicit human/admin actions.

**Why:** matches this project's established preference for minimal schema (reuse an existing persona/entity with an added mechanic rather than invent a parallel one) and for mapping a governance rule to an already-covered mechanism where one exists — but here, honestly noting when one does *not* exist rather than force-mapping onto something unrelated, and originating a new one instead.

**How to apply:** see `PHASE_0_PACKAGE_K_MARKETING_AND_MEDIA_IMPLEMENTATION_REPORT.md` (backend) and `MARKETING_AND_MEDIA_IMPLEMENTATION_REPORT.md` (frontend) for full implementation detail. [[video-producer-worker]] is this package's new operational persona; [[marketing-manager-worker]] and [[content-production-worker]] are unchanged personas this package builds real workflow mechanics around.

## ADR-016 — Federation Registry & External AI Consulting: real consultation flow over a cosmetic provider layer, a deterministic confidence heuristic, and no new pricing tier

**Status:** Approved (user-confirmed design decisions), 2026-08-17. **Source:** user-approved design decisions during Phase 0 Package L planning.

A repo-wide search confirmed "Federation" was entirely greenfield before this package — no prior reference anywhere in either repo. Package L introduces `FederationProvider` (a global, non-organisation-scoped registry — same precedent as `MarketplaceListing` — doubling as objective #2's model capability catalogue via its own `capabilities` field, rather than a second table), `FederationConsultation`, and `FederationAuditLog`. Unlike every prior external integration in this project (Package 8's Connectors, Package J's CRM connectors, Package K's YouTube connector — all permanently cosmetic stubs, each with a real *native* feature that worked regardless), Federation's whole point is the consultation experience itself, so the confirmed design keeps the registry/confidence/selection/audit machinery genuinely real and working while only the literal external HTTP call is simulated: `services/federation_service.py#consult_federation()` generates every "federation response" via a real local Ollama call, always persisting `is_simulated=True`. The dead-code connector stub classes (`services/federation_providers/`) mirror the Package 8/J/K shape exactly but are never imported by the real consult flow, exactly as those packages' own native CRUD never routed through their own stub connectors.

Confidence (objective #8) is a deterministic keyword-overlap heuristic (`services/federation_service.py#compute_confidence()`, reusing `services/orchestration_service.py#significant_words()`), not a model-generated score — the same "algorithm over model judgment" principle this project's own `_pick_worker_for_subtask()`/`suggest_consultation()` already apply, avoiding a new class of "trust the model's own claim" risk. Federation gates at Platinum (`"federation_consultation"` in `_CAPABILITY_MIN_TIER`) alongside `cto_orchestration`/`orchestration_intelligence` — the existing ceiling of `_TIER_ORDER` — rather than introducing a new tier, which would be a separate, much larger commercial conversation this package doesn't open. Cost/usage tracking (objective #9) is scoped to federation consultations only; `services/ollama_service.py`, used by every other package, is untouched.

**Governance mapping:** "use Teracom capabilities first / consult federation only when confidence is insufficient or specialist expertise is required" is the suggest-then-confirm shape `POST /federation/suggest` → `POST /federation/consult` already established by `POST /orchestration/suggest` → `POST /orchestration/consult` — the confirm action still permits a human to name a specific provider even when confidence was fine (the "specialist expertise required" clause), consistent with this project's standing "the human decides, the system informs" pattern; it does not hard-block on the confidence check. "No external model may commit commercial, contractual, or financial actions" is satisfied the same way ADR-013/014 already established for this exact class of rule: there is no code path anywhere in this backend where any AI-generated text (local or federation) executes a commercial/financial action — reused reasoning, not a new mechanism, and doubly true here since no real external model is even called. "Federation activity must be auditable" is `FederationAuditLog`, mirroring the four existing audit-log models' shape exactly. "Federation governance controls" (objective #6, its own concrete deliverable) is a new admin-only, per-organisation toggle — `Organisation.federation_enabled` + `PATCH /organisations/federation-enabled`, mirroring the existing `PATCH /organisations/industry` endpoint's exact shape — checked by both `suggest_federation_escalation()` and `consult_federation()`'s callers in addition to the tier gate. "Human approval rules remain unchanged" / "preserve existing governance rules" is purely additive — verified by the full pre-existing test suite passing unmodified.

**Why:** matches this project's established preference for minimal schema and for reusing proven mechanisms (the consult-then-synthesise shape, the connector-stub pattern, the audit-log shape, the tier-gating mechanism) over inventing new ones, while being honest that Federation's core value — the consultation experience — cannot itself be a dead stub the way a peripheral integration could be.

**How to apply:** see `PHASE_0_PACKAGE_L_FEDERATION_AND_EXTERNAL_AI_CONSULTING_IMPLEMENTATION_REPORT.md` (backend) and `FEDERATION_AND_EXTERNAL_AI_CONSULTING_IMPLEMENTATION_REPORT.md` (frontend) for full implementation detail. No new worker persona was introduced — Federation is infrastructure available to any owned worker's consultation flow.

## ADR-017 — CFO & Finance Platform: three parallel operational personas, extending Proposal/Quote/Contract's approval shape rather than originating a new one, and a correction to this project's own stale billing-backend claim

**Status:** Approved (user-confirmed design decisions), 2026-08-17. **Source:** user-approved design decisions during Phase 0 Package M planning.

Unlike Marketing Manager Worker (Package K), which has always filled both its own operational role and the Head of Marketing role at once, CFO Worker's own doc has always been advisory-only — structurally identical to Head of Sales/Head of Customer Success before Package J built their operational counterparts. Package M introduces `DepartmentBudget` (a new table, mirroring `Proposal`/`Quote`/`Contract`'s submit → organisation-admin-decide shape exactly — the applicable precedent, per ADR-014, since this is internal to the customer's own organisation, not Teracom's separate staff-decides licensing plane) and `Proposal.internal_cost_estimate` (a single new nullable column, matching the precedent `amount` itself set — an internal cost-to-deliver figure, distinct from the customer-facing price, not itself a pricing decision and so not approval-gated). Finance Manager Worker, Cost Analyst Worker, and Licensing Analyst Worker are three genuinely new operational personas — but unlike Package K's sequential Marketing Manager → Content Producer → Video Producer pipeline, they are **three parallel specialties** with no natural production handoff between budget management, cost analysis, and licensing analysis. Licensing Analyst Worker's own doc explicitly disambiguates itself from the pre-existing, differently-scoped Licensing & Compliance Worker (Package D) — an operational customer-data-analysis role, not a licensing-mechanism/compliance-design role.

Objective #7 (organisation cost visibility) and objective #8 (federation cost tracking integration) are satisfied by `services/finance_summary_service.py#get_finance_summary()` reusing `services/federation_summary_service.py#get_federation_summary()`'s already-working `total_estimated_cost` aggregate unmodified — no change to Package L's own models or service. Objective #9 (AI usage cost reporting) stays scoped to that same Federation-only simulated figure; `services/ollama_service.py`, used by every other package's AI-assist call, remains untouched, per the confirmed decision.

**A correction to this project's own documentation, made as part of this package's research:** `PROJECT_STATE.md` had stated "zero billing/licensing backend support of any kind exists — not even a stub," a claim accurate only before backend Phase 0 Packages A–D shipped `Licence`/`LicenceRequest`/`Entitlement`/`HardwareFingerprint`/`LicensingAuditLog` — real, complete, migrated tables every package's own e2e test already exercises via `_grant_active_licence()`. What is genuinely still missing is the *commercial billing layer*: no price, invoicing, payment, or `Subscription` entity exists anywhere (`models/licence.py`'s own docstring says so explicitly). Objective #10 (licensing and subscription tracking) is scoped accordingly: `services/finance_summary_service.py`'s `licensing` section surfaces the organisation's real, existing licence/entitlement data; subscription tracking is honestly represented as not-yet-built, not silently ignored or falsely claimed as present.

**Governance mapping:** "no automated spending / purchasing / contract signing" is satisfied the same way ADR-013/014/016 already established — no code path anywhere in this backend lets any worker's output execute a spending, purchasing, or signing action; a `DepartmentBudget` approval is a recorded figure, not a triggered payment. "Human approval required for all financial commitments" is `DepartmentBudget`'s new submit → admin-decide gate plus `Quote`/`Contract`'s pre-existing gate (Package J, unchanged) — reused reasoning extended to a new entity, not a new mechanism. "Human approval required for all pricing decisions" remains `Quote`/`Contract`'s existing gate, entirely unchanged; `Proposal.internal_cost_estimate` is explicitly not a pricing decision and so carries no gate of its own.

**Why:** matches this project's established preference for extending a proven approval shape (Proposal/Quote/Contract's submit → admin-decide) to a new entity rather than inventing a second mechanism, for keeping schema minimal (a single new column for internal cost, a new table only where a genuine approval lifecycle exists), and for correcting a documentation claim discovered to be stale rather than leaving it uncorrected — consistent with `PROJECT_STATE.md`'s own stated rule that "if it disagrees with the code, the code wins."

## ADR-018 — Operations & Project Delivery Platform: two different retrofit patterns in one package, an ungated approval shape extending OnboardingTask rather than Proposal/Quote/Contract, and closing a standing department-scoping gap for the new entity

**Status:** Approved (user-confirmed design decisions), 2026-08-17. **Source:** user-approved design decisions during Phase 0 Package N planning.

Package N is the first package in this series to close two advisory-only-persona gaps at once, using the two different patterns already established by prior packages rather than picking one for both. Head of Operations Worker's own doc has always been advisory-only — structurally identical to Head of Sales/Head of Customer Success before Package J, and to CFO Worker before Package M — so it receives a genuinely new operational doer, Operations Manager Worker (the Package J/M pattern). Project Manager Worker, by contrast, has always had a clear product-facing definition ("planning, sequencing, cross-team coordination") that already described project/task delivery work directly, so it receives Marketing Manager Worker's own Package K treatment instead: real mechanics grafted onto the existing persona, no second advisory-only persona introduced first.

The data model is two new tables, `Project` and `Task` (no separate `Milestone` table, per the confirmed decision — matches this project's "no premature abstraction" convention). Unlike `CrmContact`/`Campaign` (always organisation-wide, a gap flagged in two prior packages' own risk lists), `Project.department_id` is nullable — a project may optionally belong to one department. This was not one of the four confirmed design forks; it was decided during planning specifically to avoid repeating the same flagged gap a third time on a new entity, while staying optional so it doesn't force every project into a department.

**Project/Task creation and status changes carry no approval gate** — any organisation member may create either and change status directly. This extends `OnboardingTask`'s existing precedent (Package J: create-and-progress, no submit/decide step) rather than `Proposal`/`Quote`/`Contract`/`DepartmentBudget`'s submit → organisation-admin-decide shape (Package J/M) — the applicable precedent here, since project/task tracking is operational execution tracking, not a financial or contractual commitment. `OperationsAuditLog` still records every `project_created`/`task_created`/`task_completed` event, mirroring `FinanceAuditLog`'s own "audit even when ungated" discipline (Package M logged `proposal_cost_estimated` despite also carrying no gate).

`Department.function` gains a fifth value, `"operations"`, for dashboard/identity purposes only, per the confirmed decision — the standing gap where `Department.function` isn't wired into CTO Orchestration's delegation routing (flagged since Package J, again at K and M) stays deferred; this package does not touch `_pick_worker_for_subtask()`.

**Governance mapping:** nothing in this package's own new code is AI-generated or model-suggested — every new endpoint is either human-entered structured data (project/task creation, status changes) or a read-only aggregate (`GET /operations/summary`), the same posture Package M's finance data took. No new tier-gated capability was needed as a result.

**Why:** matches this project's established preference for reusing the shape closest to the entity's actual nature (ungated execution tracking looks like `OnboardingTask`, not like a financial commitment) rather than defaulting to the heaviest-weight precedent available, for closing a previously-flagged gap opportunistically when a new entity's own shape allows it without expanding scope, and for picking whichever of this catalogue's two established retrofit patterns (new doer vs. existing-persona retrofit) actually fits each specific persona's documented history, rather than applying one pattern uniformly across a package that happens to touch two personas at once.

**How to apply:** see `PHASE_0_PACKAGE_N_OPERATIONS_AND_PROJECT_DELIVERY_IMPLEMENTATION_REPORT.md` (backend) and `OPERATIONS_AND_PROJECT_DELIVERY_IMPLEMENTATION_REPORT.md` (frontend) for full implementation detail. ## ADR-019 — Customer Portal & Self-Service Platform: a new narrower-than-organisation identity plane modelled on the staff plane's mechanism, a unified support/incident/communications model, automatic incident-to-Task creation, and a non-overloaded naming convention

**Status:** Approved (user-confirmed design decisions), 2026-08-17. **Source:** user-approved design decisions during Phase 0 Package O planning.

Every package through Package N built tools for an organisation's own internal users — a `User` row scoped to exactly one `organisation_id`. Package O is the first to expose a portal to an organisation's *own customers* — external parties who, before this package, were only `CrmContact` business records with zero login capability. Research confirmed no precedent anywhere in this codebase for an identity scoped *narrower* than an organisation; the only adjacent precedent, `staff_users` (Teracom's own cross-tenant employees), goes the opposite direction — broader, not narrower. `PortalContact` originates this narrower plane, mirroring `staff_users`' mechanism structurally (a separate table, a separate JWT audience claim on the same signing key, a separate auth dependency function that must never share a code path with any other identity) while solving the opposite scoping problem: a `PortalContact`'s JWT resolves to exactly one `crm_contact_id`, and every portal-contact route filters on that id, not just `organisation_id` — a strictly narrower isolation boundary than any prior package's own organisation-level check.

**The concrete mechanism behind "customers may view their own information only" is a distinct response shape, not just a query filter.** `schemas/portal_contact_view.py`'s `PortalProposalView`/`PortalQuoteView`/`PortalContractView` deliberately omit `internal_cost_estimate`, `decision_notes`, and internal user ids — fields the existing internal `ProposalResponse`/etc. carry. This makes leaking internal-only financial or decision metadata to a customer structurally impossible rather than a matter of correctly remembering to filter it out at every call site.

Objectives #7 (support), #8 (incidents), and #10 (communications timeline) are served by one unified model — `SupportRequest` (a `request_type` discriminator, `"support"`|`"incident"`) plus one `SupportRequestMessage` thread table, whose aggregated content across a contact's own requests *is* the communications timeline — rather than three separate systems for three objectives that substantially overlap in shape (raise something, exchange messages, progress status). **Incident-type submission automatically creates a Task** under an auto-created-if-missing "Customer Incidents" `Project` (Package N's model, reused, not duplicated) — the literal reading of governance's "incident reports create operations workflows" (not "may create"). No code path anywhere in this package triggers a deployment, infrastructure change, or any external action; only a tracked, recorded unit of work is created.

Two further additive design calls made during planning, not asked as forks: `Project` gained a nullable `crm_contact_id` (staff may link a project to the customer it's being delivered for — the mechanism behind objectives #2/#9), and `Knowledge` gained a nullable `customer_visible` boolean (the mechanism behind objective #11's self-service access, reusing the existing knowledge model rather than building a second one). `Project.created_by_user_id` was loosened to nullable to accommodate the one system-created "Customer Incidents" Project, which has no human creator.

**Naming:** this codebase's own docs already use "customer" to mean the paying organisation and "staff" to mean Teracom's own employees. Rather than introduce a third, colliding meaning, the new identity plane is named `PortalContact` throughout code and internal docs — "Customer Portal" is reserved for user-facing product copy only. The frontend gets its own route group (`/customer-portal`), its own session cookie (`teracom_portal_contact_session`), and its own authoritative session-check route, per ADR-005's own stated escape hatch for a materially different auth state — never sharing a code path with the existing `/portal` session plane, mirroring the backend's own auth separation.

**Governance mapping:** "customers may view their own information only" is the `PortalContact` JWT + slim response-schema mechanism above. "Cross-customer isolation must be enforced" is tested explicitly — narrower than every prior package's organisation-level isolation check. "Financial approvals remain human-controlled" / "contract approvals remain human-controlled" — the portal-contact plane has zero write capability on `Proposal`/`Quote`/`Contract` of any kind; the existing staff-only decide routes (Package J) are completely unchanged. "Incident reports create operations workflows but do not trigger automatic deployments" is the automatic-Task-creation mechanism above — a recorded row, never a triggered action.

**Why:** matches this project's established preference for imitating a proven mechanical pattern (the staff plane's separate-table/separate-claim/separate-dependency shape) even when solving the opposite problem, for reusing one unified model where three objectives substantially overlap rather than building three, for making a governance rule's "customers may view their own information only" a structural property of the response schema rather than a policy to remember, and for resolving a naming collision explicitly before it propagates through new code and docs, rather than leaving it implicit and confusing later.

**How to apply:** see `PHASE_0_PACKAGE_O_CUSTOMER_PORTAL_AND_SELF_SERVICE_IMPLEMENTATION_REPORT.md` (backend) and `CUSTOMER_PORTAL_AND_SELF_SERVICE_IMPLEMENTATION_REPORT.md` (frontend) for full implementation detail. No new worker-catalogue persona was introduced; [[customer-success-manager-worker]]'s existing scope is extended (not replaced) to include monitoring and responding to portal support requests.

## ADR-020 — Worker Lifecycle & Governance + Architecture Integration + Production Operations: a second, optional worker-creation path that extends ADR-013 rather than contradicting it, a deliberately scoped governance-policy registry, a keyword-boost fix for a three-package-old routing gap, and an organisation-scoped Production Operations platform

**Status:** Approved (user-confirmed design decisions), 2026-08-17. **Source:** user-approved design decisions during Phase 0 Package PQR planning.

This combined package closes three distinct kinds of gap in one change. **Worker creation requests:** ADR-013 and `DEPARTMENT_HEAD_LAYER_V1.md` §3 already declared "human approval for new worker creation" satisfied by the pre-existing admin-gated `POST /workers/` (direct creation, no request step) — a position that was correct at the time and remains correct for that specific path, which is unchanged. This package's own objectives asked for worker creation *requests* and *approval workflows* as separate, additional items, so `WorkerCreationRequest` originates a second, optional path: any org member may submit one, an admin decides it, and only approval creates a real `Worker` row from the stored fields — the "gate creation itself" mechanism, distinct from every existing submit → admin-decide entity (Proposal/Quote/Contract/DepartmentBudget), which all approve an already-existing row. This extends ADR-013's position rather than reversing it: direct admin creation remains available, unchanged, exactly as before.

**Governance policy registry:** research confirmed 24 scattered `require_role("admin")` call sites across 17 files and a binary admin/member role with no hierarchy — an already-documented, accepted limitation (ADR-006). `services/governance_policy_service.py` formalizes this into a registry mirroring `services/entitlement_service.py`'s exact shape (a flat, fail-loud `action → required_role` lookup plus one shared function) — the same "reuse an existing shape" convention this project applies consistently. **Deliberately scoped, stated explicitly rather than left implicit:** the registry is the actual enforcement mechanism for this package's own new endpoints and the read-only visibility screen (objective #7) only. The 24 pre-existing call sites are not retrofitted — a mechanical, high-file-count refactor of already-shipped, already-tested code for zero behavioural change was judged not worth the regression risk in a package already spanning three sub-domains. "Authority matrix" here means a formalized, visible mapping of the existing binary model, not new role granularity.

**`Department.function` → CTO routing:** a three-package-old flagged gap (Package J, reflagged K/M/N) is closed with the smallest change that fits: a static `_FUNCTION_KEYWORDS` dictionary, unioned into a department-head candidate's own scored words in `_pick_worker_for_subtask()` only when `department.function` is set to a known value. A department with no `function` tag — every organisation before this package — is byte-for-byte unaffected, verified by dedicated unit tests alongside the existing Package I routing tests.

**Production Operations Platform:** research confirmed this is genuinely new territory — Package N's `Project`/`Task` is customer-facing work delivery, Package O's `SupportRequest` is customer-*reported* issues, and "the platform's own operations" fits neither. Confirmed with the user: **organisation-scoped**, not a new cross-tenant staff-only plane — each organisation's own environment (relevant given Sovereign/Customer-Hosted editions each run in their own environment), reusing the existing Organisation/User model exactly like every prior package. `DeploymentRecord` is a two-step gate mirroring Package K's `MediaCentreItem` (`"ready"→"published"`): submit → admin-decide → a further, separate admin "complete" action, restating Package O's ADR-019 "no automated deployments" language at package scope rather than Package O's customer-incident-only scope. `PlatformIncident` is ungated create/status, mirroring Package N's `Task` posture. `services/production_platform_health_service.py#get_platform_health_summary()` is a computed snapshot from real rows, never a stored time series — the honest "monitoring and alerting foundation" objective #13 asks for, not fabricated uptime data or a real notification pipeline (named distinctly from the pre-existing `services/platform_health_service.py`, Package 7's own simple per-organisation resource-count check backing `GET /health/`, to avoid a genuine module-name collision caught during implementation).

**Governance mapping:** "human approval required for new worker creation" was already satisfied (direct admin creation); now additionally satisfied via `WorkerCreationRequest`'s gate for the new non-admin-initiated path. "Human approval required for organisational restructuring" / "commercial and financial commitments" are unchanged, already enforced (department/worker-department-assignment admin gates; Proposal/Quote/Contract, Package J; DepartmentBudget, Package M). "Human-triggered execution remains the default" / "bounded autonomous delegation remains unchanged" are unchanged since Package G — this package touches `_pick_worker_for_subtask()`'s scoring only, never chain-length or trigger behaviour. **New:** deployment records require admin decide-then-complete before `status` ever reaches `"completed"` — no code path anywhere touches real infrastructure.

**Why:** matches this project's established preference for extending a prior confirmed decision rather than silently reversing it when new objectives ask for more, for reusing a proven pattern shape (`entitlement_service.py`'s registry, `MediaCentreItem`'s two-step gate, `Task`'s ungated posture) over inventing a new one, for stating a scope boundary explicitly (the registry's non-retrofit of existing call sites) rather than leaving it to be discovered as an omission, and for keeping a genuinely new concern (production operations) scoped to the tenancy model that actually fits it rather than defaulting to whichever existing table looks superficially similar.

**How to apply:** see `PHASE_0_PACKAGE_PQR_WORKER_GOVERNANCE_ARCHITECTURE_AND_PRODUCTION_OPERATIONS_IMPLEMENTATION_REPORT.md` (backend) and `WORKER_GOVERNANCE_ARCHITECTURE_AND_PRODUCTION_OPERATIONS_IMPLEMENTATION_REPORT.md` (frontend) for full implementation detail. No new worker-catalogue persona was introduced — this package is infrastructure/governance work, not a new AI operational role.

## ADR-021 — Commercial Provisioning & Entitlements: completing two already-half-built request types instead of inventing a third, a new organisation-level onboarding table instead of reusing `OnboardingTask`, and entitlement enforcement scoped to the new provisioning path only

**Status:** Approved (user-confirmed design decisions), 2026-08-18. **Source:** direct instruction during Phase 0 Package Q planning — explicitly excluding billing engines and payment gateways, focused on "a completed sale results in a fully provisioned customer environment."

Research before writing any code found that `worker_pack`/`tier_change`/`hosting_change` were not missing request types to design from scratch — they already existed in `LicenceRequest.REQUEST_TYPES`, and `tier_change`/`hosting_change` already required `tier`+`hosting_model` in `api/licensing.py`'s own pre-existing validation, evidence the original Package A design always intended them to generate a licence. What was actually missing was narrower: `api/staff_licence_requests.py`'s own `_GENERATABLE_REQUEST_TYPES` restricted real generation to `initial_issuance`/`renewal`, so approving the other two did nothing. This package completes that wiring rather than inventing a fourth request-handling mechanism — `tier_change`/`hosting_change` now reuse `generate_licence()` unchanged, exactly like `renewal` already did, and `worker_pack` gets its own narrower path (`apply_worker_pack_addon()`) since it updates an existing licence's entitlement rather than issuing a new one.

**`WorkerPackAddOn` vs. `WorkerPack`:** `models/worker_pack.py`'s own docstring already named this collision explicitly — one "Worker Pack" is a curated content catalogue (persona templates, Package D), the other is a commercial +5/+10 quantity add-on (`LICENSING_MODEL_V1.md` §7). This package gives the quantity concept its own table, `WorkerPackAddOn`, rather than perpetuating the ambiguity into a new schema. `services/entitlement_service.py#recompute_worker_limit()` — the formula for combining a tier's base allocation with purchased add-ons — existed since Package B with no rows to sum; this package is "the separate, not-implemented-here Worker Packs package" that formula's own docstring pointed to.

**A new `OrganisationOnboardingTask` table, not a reuse of `OnboardingTask`:** `OnboardingTask` (Package J) is scoped to a `CrmContact` — a sales-pipeline prospect *of* the organisation, tracked by that organisation's own Sales & Customer Success workforce. This package's checklist is scoped to the organisation itself, the Teracom-licensed tenant — the same "customer" naming collision `models/portal_contact.py`'s own docstring already flagged for a different pair of concepts, avoided here the same way: a new, narrower table rather than overloading an existing foreign key with the wrong semantic.

**Entitlement (worker-limit) enforcement is real, but deliberately scoped to the new `POST /worker-pack-provisioning/` path only.** `LICENSING_MODEL_V1.md` §4 is explicit that this is "a decided policy... not yet implemented anywhere in the product." Retrofitting the same check onto the pre-existing `POST /workers/` (direct admin creation, unchanged since Package 3) and `WorkerCreationRequest` approval (Package PQR) would be a behaviour change to two already-shipped, heavily-tested endpoints exercised by a large number of other packages' own test suites — a real regression risk for a policy that was explicitly "not yet implemented anywhere" before this package touched anything, so nothing regresses by leaving those two paths as they were. Confirmed as a stated scope boundary, not an oversight, and recorded as the top follow-up item in `[[current-sprint]]`.

**Frontend: `WizardShell.js`'s `onSubmit` is now genuinely awaited, but only `WorkerPackWizard.js` was wired to a real endpoint.** `WorkerPackWizard`'s submission payload (`pack_size`/`quantity`) needs no data from `lib/licensing/referenceLicence.js`'s illustrative reference licence at all — only its separate, already-existing "current allocation" *display* figure does, which this package left unchanged. `RenewalWizard.js`/`OwnershipTransferWizard.js` were deliberately left unwired: both need a real `tier`/`hosting_model`, and `OwnershipTransferWizard` a real `existing_licence_id`, none of which exist outside the illustrative reference data this package did not replace. Submitting a real request built from fabricated licence data would be a worse outcome than the existing honest "recorded on this screen only" mock — a real backend request with wrong tier/hosting fields is a genuine data-quality risk a staff approver could act on, not merely a cosmetic gap.

**Governance mapping:** "commercial and financial commitments require human approval" is unchanged and, for the first time, actually load-bearing beyond licensing itself — a `worker_pack`/`tier_change`/`hosting_change` approval now visibly does something. "Customers may only access what they're entitled to" gains its first real enforcement point (`worker_pack_provisioning`'s worker-limit check), narrower than the full policy but a genuine first instance rather than zero.

**Why:** matches this project's established preference for completing an already-half-built mechanism over inventing a parallel one once research reveals the gap is narrower than the package's own name implies, for giving a genuinely distinct commercial concept (the quantity add-on) its own table rather than perpetuating a documented naming collision into new schema, and for treating "this policy isn't enforced anywhere yet" as licence to enforce it on new surface area without destabilizing already-shipped, already-tested surface area — the same restraint ADR-020 applied to the governance-policy registry's own non-retrofit of the 24 pre-existing `require_role("admin")` call sites.

**How to apply:** see `PHASE_0_PACKAGE_Q_COMMERCIAL_PROVISIONING_AND_ENTITLEMENTS_IMPLEMENTATION_REPORT.md` for full implementation detail. No new worker-catalogue persona was introduced — this package is commercial/provisioning infrastructure, not a new AI operational role.

## ADR-024 — Package CX1: identity-plane rate limiters must be separate instances by construction, trial lifecycle as computed-not-stored state, and a production runtime lesson about restarting after a rebuild

**Status:** Approved (user-confirmed design decisions), 2026-08-18. **Source:** direct instruction for the "Customer Experience & Commercial Readiness Wave," four blocking questions resolved up front (email = abstraction-only, AI Concierge = foundation-only, trial expiry = grace period then Locked Mode, objective 18 dropped).

**A real cross-identity-plane bug was found and fixed, not just avoided by convention.** `api/portal_contact_auth.py`'s forgot-password endpoint was written importing `password_reset_rate_limiter` — the same `SlidingWindowRateLimiter` instance the internal-`User` plane's own forgot-password endpoint uses. This is exactly the kind of state-sharing ADR-019 established the `PortalContact` plane must never do, and it was caught only because the full test suite (not an isolated test run) exposed the shared, unreset, process-wide singleton state across test files. The fix — a second, dedicated `portal_contact_password_reset_rate_limiter` instance, same config, separate object — is now the template: **any new rate-limited endpoint on a distinct identity plane gets its own limiter instance at construction time, never a reused reference,** even when the limiting logic and thresholds are identical. The regression test protecting this was itself rewritten after an HTTP-level version proved order-dependent under full-suite conditions; the surviving version asserts directly against the two Python objects with a fixed, guaranteed-unused probe IP (TEST-NET-3, RFC 5737) — a pattern worth reusing for any future test of this rate limiter's cross-endpoint isolation, since testing through HTTP re-introduces the exact suite-ordering fragility that caused this bug's own regression test to fail once already.

**Trial lifecycle (grace period → Locked Mode) follows the same computed-not-stored pattern `licence_validation_service.py` already established**, for the same reason: this backend has no background scheduler, so nothing can "advance" a trial's state on a timer. `trial_service.py#get_trial_status()` derives `"active"`/`"grace"`/`"locked"` fresh from `trial_ends_at` and a `TRIAL_GRACE_PERIOD_DAYS` config constant on every call; the only persisted state is two nullable timestamp columns (`trial_grace_notified_at`/`trial_locked_notified_at`) that exist solely to guarantee each lifecycle notification fires exactly once, not to cache the status itself. This means an organisation nobody ever queries (no login, no `/auth/me` call) will sit in an un-notified state indefinitely — an accepted consequence of not building a scheduler for this package, not an oversight.

**A production operations lesson, confirmed twice in one wave:** rebuilding the frontend (`rm -rf .next && npm run build`) without restarting `teracom-frontend.service` leaves the long-running process serving a stale in-memory `BUILD_ID` against a new on-disk build, producing exactly the `ENOENT`/404 symptoms a user-reported incident caught mid-wave (see the implementation report §5). The same mistake was nearly repeated a second time during this package's own final build step (§8) and was caught by the same lesson being applied proactively — restart immediately after every rebuild, verify the restart timestamp postdates the build, and curl real asset paths from the live HTML rather than trusting an HTTP 200 on `/` alone. Worth stating as a standing rule for every future package's own final-validation step, not just this one's.

**Why:** matches this project's established preference for a dedicated limiter instance per identity plane over a shared one (ADR-019's own isolation principle, now extended from data access to rate-limiting state), for computed-not-stored derived state when no scheduler exists (`licence_validation_service.py`'s precedent), and for verifying a live production service directly rather than trusting a successful build alone — the same discipline Platform Review Wave 1's middleware fix and this package's own §5/§6 incidents both depended on.
